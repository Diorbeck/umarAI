# QA Learning Log — Умар

## Сессия 1 — 27.07.2026 — первичный аудит daruz.uz (v1)

**Что получилось хорошо:**
- Ядро процесса сработало: план → карта рисков → проверка → воспроизведение ≥2 раз → отчёт с доказательствами; найдены реальные проблемы (мобильная вёрстка, SEO, мёртвые ссылки, карта).
- Быстрая адаптация: облачная среда не имела доступа к сайту — переключился на Chrome пользователя без потери задачи.
- Позитивные проверки зафиксированы отдельно (что работает надёжно) — владельцу видно не только плохое.

**Какие ошибки допустил:**
1. Абсолютные формулировки без достаточных доказательств: «сайт невидим для Google», «мобильная версия фактически отсутствует» — при том что мобильность проверялась эмуляцией, а индексация не проверялась вовсе.
2. Назначил CRITICAL мобильному багу до подтверждения на реальном устройстве.
3. Оставил открытые телефоны продавца в тексте отчёта и на скриншоте (10-contact-modal.jpg) — персональные данные в общем документе.
4. Избыточная доказательная база для простых багов (25 скриншотов, часть дублируется) — время потрачено на упаковку, а не на поиск проблем.

**Правила, чтобы не повторить (добавлены в постоянные):**
- Каждое утверждение помечать: подтверждённый факт / вероятный баг / гипотеза / бизнес-риск.
- Формулировать влияние через «может приводить к…», если прямого замера нет.
- CRITICAL — только когда основной процесс полностью недоступен, теряются деньги/данные или большинство пользователей не может работать.
- Обычному багу достаточно: шаги, факт/ожидание, 1 скриншот, повтор, влияние на пользователя.
- Телефоны/email в отчётах маскировать (+998 90 1** ** 38).

**Что улучшу в следующем тесте:**
- Начну с «минимального пакета» доказательств и буду расширять его только для критических/спорных багов.
- Ограничения методики (эмуляция vs реальное устройство) буду указывать прямо в строке вердикта бага, а не в сноске.
- Скриншоты с персональными данными — маскировать до включения в отчёт.
